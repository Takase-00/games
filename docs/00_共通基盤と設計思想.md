# アプリ制作プロジェクト：共通基盤と設計思想

この資料には、このプロジェクトで作るすべてのアプリに共通する作り方と考え方だけをまとめています。

アプリごとの仕様（ルール、パラメータ、公開リンク、変更履歴など）は、各アプリのチャットに渡す個別の仕様書で管理します。この資料には書きません。

---

## 1. プロジェクトの進め方

### 1-1. チャットの使い方

- 1つのチャットでは、1つのアプリだけを扱う
- アプリの個別仕様書は、そのアプリのチャットに渡す
- 既存のアプリを改修するときは、チャットに貼られたClaude上の公開リンクから最新のファイルを読み込み、それをもとに作業する
- 新しいアプリは、新しいチャットで企画から始める
- GitHubで一般公開したあとのアプリは、手元のリポジトリを最新版とし、Claude Codeで改修する（詳しくは「00_開発の進め方.md」）

### 1-2. 役割分担

| 担当 | 作業 |
|---|---|
| Claude | 企画の具体化、実装、動作確認、不具合の修正、版番号の更新、Claude上での公開（Artifact）、個別仕様書の作成と更新内容のまとめ。Claude Codeでは、承認を得たうえでのコミットまで |
| 管理者 | 一般公開（GitHubへのアップロード・マージ・push・タグの公開、Artifactの共有設定の変更、公開先URLの管理など） |

- **Claudeの作業は、ゲームを作成し、Claude上で遊べる状態にするところまで**
- 一般公開に関わる作業（外部サービス向けのファイル作成、公開手順書の作成、共有設定の変更など）は管理者が行う。Claudeは、管理者から個別に頼まれたときだけ手伝う

### 1-3. 不具合はすぐ直す

- バグや表示崩れを見つけたら、その場ですぐ直す。頼まれた作業の途中で見つけたものも、後回しにせず直す
- ユーザーから不具合の報告があったら、最優先で原因を調べて直す
- 直したあとは、5章の手順で再確認する
- 作業の最後に「何が起きていたか」「何を直したか」を短く報告する

### 1-4. 作業の最後にまとめること

アプリを作成・改修したら、作業の最後に、個別仕様書へ反映すべき内容をまとめて出します。

- 新しい版番号（7章のルールで決める）
- 変わった仕様やルール
- 変わった主要パラメータ（数値や計算式）
- 変更履歴に追加する1行（日付・版・内容）

文書が必要なときは、Markdown（.md）ファイルで作成します。

## 2. 設計思想（ゲームデザイン）

### 2-1. 短く終わるミニゲームにする

- 1回のプレイは1〜3分。スキマ時間に遊べて、終わったらすぐ「もう一度」を押したくなる長さにする
- 終わり方は、次のどれかで必ず区切りをつける
  - 時間制（例：60秒）
  - 回数制（例：8ステージ、12日間）
  - ゲームオーバー制

### 2-2. 日常の題材に、ひとひねりを加える

- 誰でも知っている日常の題材を選び、既存のゲームにない仕組みを1つ足す
- ルールは、タイトル画面の3行程度で伝わることを目指す
- 言葉だけでは伝わりにくい場合は、タイトル画面の後ろでCPUが自動で遊ぶ「お手本デモ」を流す

### 2-3. 結果をシェアしたくなる終わり方にする

- 最後に「点数」と「称号」を出す。称号は、思わず人に見せたくなる言葉にする
- 結果画面は、そのゲームの世界観に合った1枚絵にする（題材に関係する紙、看板、ステージなどに見立てる）
- 「結果をシェア」ボタンで、点数と称号入りの投稿文を自動で作る

### 2-4. うまく遊んでも、変に遊んでも楽しくする

- 正解のルートだけでなく、失敗や偏ったプレイにも見返りを用意する。評価の軸を2つ以上にするのも有効（例：「美しさ」と「おもしろさ」）
- 失敗したときも演出を入れて、失敗そのものを楽しめるようにする
- 成長や変化は控えめにせず、はっきり見えるくらい大げさにする。極端なプレイでは、画面からはみ出しそうなくらいでよい

### 2-5. 1作品に1つ、印象に残るビジュアルを決める

- 題材から見た目のモチーフを1つ引き出し、色・形・フォント・演出をそれでまとめる
- フォントはGoogle Fontsから、モチーフに合うものを1〜2種類選ぶ
- どこかで見たようなテンプレート的な見た目は避ける

### 2-6. 色だけに頼らない

- 色の区別がつきにくい人でも遊べるように、色と一緒に記号・形・文字を使う

## 3. 技術基盤

### 3-1. ファイル構成

- 1つのアプリは1つのHTMLファイルにまとめる。CSSとJavaScriptもファイル内に直接書く
- 外部から読み込むのはGoogle Fontsだけ。読み込めなくても標準のフォントで動くようにする
- 画像・音声ファイルは使わない。見た目はCanvas・SVG・CSSで描き、音はWeb Audio APIでその場で作る
- ライブラリは使わず、素のJavaScriptで書く

### 3-2. 描画方式の選び方

| 方式 | 向いているもの |
|---|---|
| Canvas | 物が常に動く、物理的な動き、たくさんの物体 |
| DOM（HTMLの要素） | ボタン操作が中心、文字や数字の表示が多い |
| SVG（文字列で生成） | キャラクターなどの形を、数値に応じて変形させる |

SVGで形を変形させる場合は、数値から輪郭の点を計算し、Catmull-Rom曲線などでなめらかにつないで描き直します。

### 3-3. 画面と状態の管理

- `state` 変数で画面を切り替える（例：`'title'` → `'playing'` → `'over'`）
- タップなどの入力は、必ず `state` を確認してから受け付ける
- ゲームループは `requestAnimationFrame` を使う。前のフレームからの経過時間 `dt` で動かし、`dt` の上限を0.05秒にする（タブを切り替えて戻ったときに、物が瞬間移動しないように）
- 広い画面では、遊べる幅を `Math.min(画面幅, 480〜520)` に制限する。PCで遊んだときに速すぎたり簡単すぎたりしないように
- 画面サイズに左右される位置は、0〜1の割合で持っておくと、サイズが変わっても崩れない

### 3-4. スマホ対応

- viewportは次の形にする
  ```html
  <meta name="viewport" content="width=device-width, initial-scale=1, viewport-fit=cover">
  ```
- `:root` に `padding-top: env(safe-area-inset-top)` と `padding-bottom: env(safe-area-inset-bottom)` を入れて、ノッチやホームバーに重ならないようにする
- 縦画面での利用を前提にする。タップする部品は44px以上
- ゲーム領域には `touch-action: none`、UI中心の画面には `touch-action: manipulation` を指定し、ダブルタップでの拡大やスクロールの誤作動を防ぐ
- 長押しメニューと文字選択を無効にする（`user-select: none`、`contextmenu` イベントの抑止）

### 3-5. ライト・ダークモード

色はすべて `:root` のCSS変数で定義し、次の3か所に書きます。

```css
:root{ --bg:#EEF0F3; --ink:#16191E; }                     /* ライト */
@media (prefers-color-scheme: dark){
  :root:not([data-theme="light"]){ --bg:#111317; --ink:#ECEFF3; }
}
:root[data-theme="dark"]{ --bg:#111317; --ink:#ECEFF3; }   /* 表示側から指定されたとき */
```

- Canvasで描く場合は `getComputedStyle` で変数を読み取り、テーマが変わったら読み直す
- ゲーム内の「物」（お金、紙、人物の肌、空など）は、テーマに関係なく現実の色のまま固定してよい

### 3-6. 保存（ベスト記録・設定）

- `localStorage` を使い、読み書きは必ず `try/catch` で囲む。使えない環境でもゲームが止まらないようにするため
- キー名は「アプリの略称-項目」にする（例：`略称-best`、`略称-muted`）。使うキーは個別仕様書に書く

```js
function load(k, d) { try { const v = localStorage.getItem(k); return v === null ? d : v; } catch (e) { return d; } }
function save(k, v) { try { localStorage.setItem(k, String(v)); } catch (e) {} }
```

### 3-7. 効果音

- ブラウザの自動再生の制限があるため、最初にタップされたときに `AudioContext` を作る
- 共通の `tone()` 関数で鳴らす。画面右上にミュートボタンを置き、状態を保存する

```js
let actx = null;
function ensureAudio() {
  try {
    if (!actx) { const AC = window.AudioContext || window.webkitAudioContext; if (AC) actx = new AC(); }
    if (actx && actx.state === 'suspended') actx.resume();
  } catch (e) {}
}
// 周波数, 長さ(秒), 波形, 音量, 終わりの周波数(任意), 開始の遅れ(任意)
function tone(f, dur, type, vol, f2, delay) {
  if (muted || !actx) return;
  const t = actx.currentTime + (delay || 0), o = actx.createOscillator(), g = actx.createGain();
  o.type = type; o.frequency.setValueAtTime(f, t);
  if (f2) o.frequency.exponentialRampToValueAtTime(f2, t + dur);
  g.gain.setValueAtTime(0.0001, t);
  g.gain.exponentialRampToValueAtTime(vol, t + 0.01);
  g.gain.exponentialRampToValueAtTime(0.0001, t + dur);
  o.connect(g); g.connect(actx.destination);
  o.start(t); o.stop(t + dur + 0.03);
}
```

### 3-8. シェア機能

次の順番で試し、使えた方法で投稿してもらいます。

1. `navigator.share`（スマホの共有メニュー）
2. Xの投稿画面を新しいタブで開く（`https://x.com/intent/post?text=…`）
3. 上の2つが使えなければ、投稿文をクリップボードにコピーして「コピーしました」と表示する

- Claude上の版では、投稿文にURLを入れない（URLがClaude内部のものになるため）
- 一般公開用のURLやハッシュタグの追加は、管理者が公開するときに行う

### 3-9. アクセシビリティ

- 操作する部品は `<button>` を使う。アイコンだけのボタンには `aria-label` を付ける
- `prefers-reduced-motion`（動きを減らす設定）が有効なときは、アニメーションを控える
- 結果の点数などは `aria-live` で読み上げられるようにする

## 4. 実装上の注意（過去の不具合から決めた標準）

| 注意点 | 理由 |
|---|---|
| 基本CSSに必ず `[hidden]{display:none !important}` を入れる | 要素に `display:grid` などを指定すると、`hidden` 属性より優先され、隠したはずの画面が表示されてしまう |
| グリッドやフレックスの中に置くSVGは、親要素とSVG自体に `display:block` を指定する | `height:100%` が効かず、SVGが枠からはみ出して大きく表示されることがある |
| 吹き出し・数値・ラベルなどの置き場所は、ゲームの描画範囲とは別に先に確保する | あとから空いている場所に足すと、キャラやゲーム画面に重なりやすい |
| 形が大きく変わるものは、表示範囲（viewBoxなど）を中身に合わせて広げる | 極端な値のときに画面外へはみ出さないように |

## 5. 品質確認の手順

作成・改修・不具合修正のあとは、次の4段階で確認します。

1. **構文チェック**：HTMLからscript部分を取り出し、`node --check` で文法エラーがないか確認する
2. **ロジックの自動テスト**：画面部品を簡易的な代役に置き換えてNode.jsで動かし、最適なプレイやランダムなプレイを何百回も自動で回す
3. **スマホ画面での確認**：Claudeの作業環境にあるヘッドレスブラウザ（Playwright）で、390×760（iPhone相当）の画面を開く。実際にボタンを押して最後までプレイし、スクリーンショットで表示崩れを、ページエラーの記録でバグを確認する
4. **極端なケースの確認**：値が最小・最大のときや、偏ったプレイをしたときに表示が破綻しないかを、複数パターンを並べた画像で確認する

確認中に見つかった問題は、1-3のとおりその場で直し、もう一度確認します。

## 6. 新しいアプリを作るときの流れ

1. **企画**：日常の題材と、ひとひねりを決める。1回のプレイ時間、終わり方、称号の種類も決める
2. **見た目**：題材から引いたモチーフとフォントを決める
3. **実装**：1つのHTMLファイルで作り、3章の基盤（スマホ対応、テーマ、保存、音、シェア）と4章の注意点を入れる。版番号は v1.0 から始める
4. **確認**：5章の手順で確認し、見つかった問題を直す
5. **公開**：Artifactとして公開し、Claude上で遊べる状態にする（一般公開は管理者が行う）
6. **仕様書**：8章の形式で個別仕様書を作る

### 新しいアプリのチェックリスト

- [ ] タイトル画面の3行程度でルールが分かる
- [ ] 1〜3分で終わり、すぐに「もう一度」できる
- [ ] 結果に点数と称号があり、シェアボタンがある
- [ ] スマホの縦画面（390×760）で表示が崩れない
- [ ] ライトモードとダークモードの両方で文字が読める
- [ ] `[hidden]{display:none !important}` を入れた
- [ ] `localStorage` の読み書きを `try/catch` で囲んだ
- [ ] ミュートボタンがある
- [ ] 色だけで区別させていない
- [ ] タイトル画面に版番号を表示した
- [ ] Claude上で最後まで遊べることを確認した

## 7. バージョン管理

### 7-1. 版番号の付け方

版番号は「v＋メジャー番号.マイナー番号」で表します（例：v2.1）。

| 変更の種類 | 上げる番号 | 例 |
|---|---|---|
| ルールや仕組み、画面構成が変わる。大きな機能を追加する | メジャー番号を1つ上げ、マイナー番号を0に戻す | v2.3 → v3.0 |
| 数値の調整、演出の追加・変更、不具合の修正 | マイナー番号を1つ上げる | v2.3 → v2.4 |

- 新しいアプリは v1.0 から始める
- 版は「1回の作業」ごとに1つだけ上げる。同じ作業の中で複数の修正をしても、まとめて1つの版にする
- 一般公開のための調整（シェア文へのURL追加、OGPなど）だけでは版を上げない

### 7-2. 版番号を書く場所

版番号は、次の4か所で必ず同じにします。

| 場所 | 書き方 |
|---|---|
| ゲームの中 | HTMLの中で `const VERSION = 'v2.1';` のように1か所だけで定義し、タイトル画面の隅など邪魔にならない場所に小さく表示する |
| 個別仕様書 | 基本情報の「現在の版」と、変更履歴の行 |
| GitHubのコミットメッセージ | `略称 v2.1: 変更内容の要約`（例：`muki v2.1: 筋肉痛の表示を修正`） |
| GitHubのタグ | 一般公開した版に `略称-v2.1` の形で付ける |

- ゲーム内に版番号を表示しておくと、公開ページが新しい版に切り替わったかをひと目で確認できる
- タグに略称を付けるのは、1つのリポジトリに複数のアプリを入れているため

## 8. 個別仕様書の書き方

アプリごとの仕様書は、次の見出しで作ります。

| 見出し | 書くこと |
|---|---|
| 基本情報 | Claude上の公開リンク、一般公開のURL（公開後）、ファイル名、描画方式、フォント、1回の時間、保存キー、現在の版 |
| コンセプト | 題材とひとひねり。発案者から出た要件があれば、それも残す |
| ルール | プレイヤーから見た遊び方 |
| 得点と称号 | 点数の計算方法と、称号の条件 |
| 画面構成 | タイトル、プレイ中、結果などの各画面に何があるか |
| 主要パラメータ | 難易度や見た目の調整に使う数値と計算式 |
| 見た目・演出 | モチーフ、色、アニメーション、効果音 |
| 変更履歴 | 日付・版・内容。不具合の修正もここに残す |
| 今後のアイデア | まだ手を付けていない改善案 |
